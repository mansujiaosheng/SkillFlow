# 代码风格与禁止事项 Skill

## 通用执行约束

- 本 Skill 面向任意软件项目、数据项目、自动化项目或 AI 协作项目，不绑定具体业务、仓库名、目录名、团队名或技术栈。
- 回答或修改前，必须先基于当前仓库的真实文件、用户本次目标和已有约定判断；禁止臆造不存在的目录、接口、配置、数据或团队规则。
- 用户指令与仓库事实、公开接口、安全底线、可回滚原则或已明确的验收标准冲突时，必须先指出冲突点和风险，再给出更稳妥的替代方案。
- 用户坚持继续时，也只能执行可回滚、可测试、不会破坏公开接口和安全底线的部分；禁止删除测试、伪造结果、绕过保护机制或扩大任务范围。
- 多个方案都可行时，必须选择影响范围更小、依赖更少、测试更明确、回滚更容易的方案。

## 功能定位

用于保持代码可读、可维护、可测试，防止低信息量命名、硬编码、重复实现和垃圾桶目录膨胀。

## 通用规则

- 遵循项目已有 formatter、linter、类型检查和命名约定。
- 新增代码必须放在职责最明确的模块，不以“方便”“通用”“先放这里”为理由创建模糊目录。
- 业务阈值、路径、开关、超参数、外部地址等应进入配置或常量层，不在逻辑中散落硬编码。
- 注释解释“为什么这样做”，不要复述代码表面含义。
- 异常处理必须保留错误上下文，禁止裸 `except` 后静默吞错。

## 禁止事项

- 禁止创建低信息量文件：`utils.py`、`helper.py`、`common.py`、`misc.py`，除非项目已有明确约定。
- 禁止新增无边界目录：`core/`、`common/`、`helpers/`、`shared/`，除非有清晰职责和文档。
- 禁止复制粘贴相似逻辑而不抽象。
- 禁止把测试专用代码混入生产逻辑。
- 禁止把配置、密钥、样例大数据直接写进代码。

## 新增代码放置判断

1. 代码的输入是什么？
2. 输出是什么？
3. 谁调用它？
4. 它依赖哪些模块？
5. 是否已有同类职责模块？
6. 是否会造成循环依赖？
7. 是否能被独立测试？

## 检查命令示例

```bash
rg -n "TODO|FIXME|print\(|console\.log|debugger" .
rg -n "utils|helper|common|misc" .
```

实际格式化和 lint 命令以项目配置为准。

## 通用输出要求

- 先给结论，再给步骤。
- 涉及命令时，给出可直接复制的命令。
- 涉及代码改动时，说明影响范围、需要补充的测试、是否需要更新文档或变更记录。
- 信息不足时，指出需要读取的项目文件或需要确认的事实；不得用猜测替代项目事实。
