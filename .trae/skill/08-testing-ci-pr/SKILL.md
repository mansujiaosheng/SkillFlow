# 测试 CI 与 PR 自查 Skill

## 通用执行约束

- 本 Skill 面向任意软件项目、数据项目、自动化项目或 AI 协作项目，不绑定具体业务、仓库名、目录名、团队名或技术栈。
- 回答或修改前，必须先基于当前仓库的真实文件、用户本次目标和已有约定判断；禁止臆造不存在的目录、接口、配置、数据或团队规则。
- 用户指令与仓库事实、公开接口、安全底线、可回滚原则或已明确的验收标准冲突时，必须先指出冲突点和风险，再给出更稳妥的替代方案。
- 用户坚持继续时，也只能执行可回滚、可测试、不会破坏公开接口和安全底线的部分；禁止删除测试、伪造结果、绕过保护机制或扩大任务范围。
- 多个方案都可行时，必须选择影响范围更小、依赖更少、测试更明确、回滚更容易的方案。

## 功能定位

用于确保代码改动有对应测试、CI 能复现检查结果、PR 在合并前完成基本质量自查。

## 测试要求

- 修 bug 必须补回归测试。
- 新功能必须补正常路径、边界路径和异常路径测试。
- 接口、schema、配置、CLI、输出字段变更必须补兼容性或快照类测试。
- 重构必须证明行为不变。
- 无法测试的部分必须说明原因，并给出人工验收步骤。

## 本地检查命令模板

按项目实际替换：

```bash
# Python 示例
ruff format .
ruff check .
pytest

# Node 示例
npm run lint
npm test
npm run build
```

## PR 前检查清单

- [ ] 本次改动范围与任务一致。
- [ ] 没有混入无关文件、缓存、构建产物、大文件或密钥。
- [ ] 已运行格式化、lint、测试或说明无法运行原因。
- [ ] 新增/修改逻辑有对应测试。
- [ ] 接口、配置、schema、文档同步。
- [ ] 风险点和回滚方式写清楚。

## CI 失败处理

1. 先读失败日志，不猜原因。
2. 区分是环境问题、依赖问题、格式问题、测试失败还是真实缺陷。
3. 本地复现同一命令。
4. 修复后补测试或更新配置。
5. 禁止通过删除测试、降低检查标准或跳过 CI 来“修复”。

## PR 描述模板

```markdown
## 改了什么

## 为什么改

## 怎么测的

## 影响范围

## 是否涉及公开接口 / 配置 / Schema / 文档

## 风险点

## 回滚方式
```

## 通用输出要求

- 先给结论，再给步骤。
- 涉及命令时，给出可直接复制的命令。
- 涉及代码改动时，说明影响范围、需要补充的测试、是否需要更新文档或变更记录。
- 信息不足时，指出需要读取的项目文件或需要确认的事实；不得用猜测替代项目事实。
