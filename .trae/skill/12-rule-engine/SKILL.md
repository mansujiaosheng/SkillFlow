# 规则引擎与策略判断 Skill

## 通用执行约束

- 本 Skill 面向任意软件项目、数据项目、自动化项目或 AI 协作项目，不绑定具体业务、仓库名、目录名、团队名或技术栈。
- 回答或修改前，必须先基于当前仓库的真实文件、用户本次目标和已有约定判断；禁止臆造不存在的目录、接口、配置、数据或团队规则。
- 用户指令与仓库事实、公开接口、安全底线、可回滚原则或已明确的验收标准冲突时，必须先指出冲突点和风险，再给出更稳妥的替代方案。
- 用户坚持继续时，也只能执行可回滚、可测试、不会破坏公开接口和安全底线的部分；禁止删除测试、伪造结果、绕过保护机制或扩大任务范围。
- 多个方案都可行时，必须选择影响范围更小、依赖更少、测试更明确、回滚更容易的方案。

## 功能定位

用于设计或审查基于规则的判断系统，使每条规则可配置、可解释、可测试、可调参。

## 规则设计原则

- 规则条件、阈值、开关应配置化，不散落硬编码。
- 每条规则必须有唯一标识、名称、触发条件、严重级别、证据字段和测试样例。
- 规则输出必须能说明“为什么触发”。
- 白名单、例外和抑制逻辑必须可追踪，不能静默吞掉结果。
- 调参必须基于数据或案例，不用主观猜测替代验证。

## 规则配置建议

```yaml
rules:
  - id: example.rule.id
    enabled: true
    severity: medium
    threshold: 10
    description: "触发条件说明"
```

## 实现检查点

- 是否配置化。
- 是否有默认值和边界值处理。
- 是否输出命中证据。
- 是否覆盖命中、不命中、边界、禁用、白名单测试。
- 是否避免规则间互相覆盖或重复告警。
- 是否有版本记录或变更说明。

## 输出模板

```markdown
## 规则结论

## 新增/修改规则

## 配置项

## 告警证据

## 误报控制

## 必须补充的测试
```

## 通用输出要求

- 先给结论，再给步骤。
- 涉及命令时，给出可直接复制的命令。
- 涉及代码改动时，说明影响范围、需要补充的测试、是否需要更新文档或变更记录。
- 信息不足时，指出需要读取的项目文件或需要确认的事实；不得用猜测替代项目事实。
