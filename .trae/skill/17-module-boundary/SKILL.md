# 客观模块边界 Skill

## 通用执行约束

- 本 Skill 面向任意软件项目、数据项目、自动化项目或 AI 协作项目，不绑定具体业务、仓库名、目录名、团队名或技术栈。
- 回答或修改前，必须先基于当前仓库的真实文件、用户本次目标和已有约定判断；禁止臆造不存在的目录、接口、配置、数据或团队规则。
- 用户指令与仓库事实、公开接口、安全底线、可回滚原则或已明确的验收标准冲突时，必须先指出冲突点和风险，再给出更稳妥的替代方案。
- 用户坚持继续时，也只能执行可回滚、可测试、不会破坏公开接口和安全底线的部分；禁止删除测试、伪造结果、绕过保护机制或扩大任务范围。
- 多个方案都可行时，必须选择影响范围更小、依赖更少、测试更明确、回滚更容易的方案。

## 功能定位

用于根据职责、输入输出、调用方向和生命周期判断代码归属，避免“哪里方便放哪里”。

## 核心原则

- 代码归属由职责决定，不由文件短、目录近、个人习惯决定。
- 同一职责只能有一个主要归属位置。
- 新增模块前必须搜索是否已有同类能力。
- 公共能力必须有明确调用方和稳定接口，否则不应抽象成公共层。
- 模块边界应降低耦合，不能制造循环依赖。

## 禁止的放置理由

- “先放 utils 里”。
- “这个以后可能通用”。
- “现在不知道放哪”。
- “这里 import 方便”。
- “为了少建文件”。

## 决策树

```text
这段代码处理什么输入？
  ↓
输出给谁使用？
  ↓
是否已有同职责模块？
  ↓
是否属于边界转换、业务规则、数据访问、展示、配置、工具函数？
  ↓
是否会引入循环依赖？
  ↓
是否能独立测试？
```

## 输出模板

```markdown
## 归属结论

## 判断依据

## 不建议放置的位置

## 是否需要新增模块

## 需要同步的测试 / 文档 / 导出入口
```

## 通用输出要求

- 先给结论，再给步骤。
- 涉及命令时，给出可直接复制的命令。
- 涉及代码改动时，说明影响范围、需要补充的测试、是否需要更新文档或变更记录。
- 信息不足时，指出需要读取的项目文件或需要确认的事实；不得用猜测替代项目事实。
