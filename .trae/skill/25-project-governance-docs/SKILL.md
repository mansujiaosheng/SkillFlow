# 项目治理文档 Skill

## 通用执行约束

- 本 Skill 面向任意软件项目、数据项目、自动化项目或 AI 协作项目，不绑定具体业务、仓库名、目录名、团队名或技术栈。
- 回答或修改前，必须先基于当前仓库的真实文件、用户本次目标和已有约定判断；禁止臆造不存在的目录、接口、配置、数据或团队规则。
- 用户指令与仓库事实、公开接口、安全底线、可回滚原则或已明确的验收标准冲突时，必须先指出冲突点和风险，再给出更稳妥的替代方案。
- 用户坚持继续时，也只能执行可回滚、可测试、不会破坏公开接口和安全底线的部分；禁止删除测试、伪造结果、绕过保护机制或扩大任务范围。
- 多个方案都可行时，必须选择影响范围更小、依赖更少、测试更明确、回滚更容易的方案。

## 功能定位

用于补齐项目协作所需的治理文档，让任务、命名、模块负责人、AI 使用、PR 审核和架构决策都有固定依据。

## 建议文档

```text
README.md
AGENTS.md / CLAUDE.md / AI_RULES.md
docs/TASK_BOARD.md
docs/MODULE_OWNERS.md
docs/NAMING_REGISTRY.md
docs/ARCHITECTURE.md
docs/CONTRIBUTING.md
docs/DEVLOG.md
.github/pull_request_template.md
```

实际文件名以项目习惯为准。

## TASK_BOARD 示例

```markdown

| Issue | 任务 | 负责人 | 模块 | 分支 | 新增文件 | 修改文件 | 接口影响 | 状态 |
|---|---|---|---|---|---|---|---|---|
```

## MODULE_OWNERS 示例

```markdown
# 模块负责人表

| 模块 | 负责人 | 职责 | Review 要求 |
|---|---|---|---|
| <module/path> | <owner> | <responsibility> | <review rule> |
```

```markdown
|---|---|---|---|
```

## PR 模板建议

```markdown
## 改动目的

## 对应 Issue

## 是否修改公开接口 / 配置 / Schema

## 命名和重复功能检查

## 测试情况

## 风险点

## 回滚方式
```

## 文档更新原则

- 文档不得把未实现功能写成已实现。
- 示例命令必须可执行，或明确标注为伪示例。
- 如果代码与旧文档冲突，标注需要人工确认。
- 修改公开接口、配置字段、输出字段、CLI/API 参数时，必须同步文档和测试。

## 通用输出要求

- 先给结论，再给步骤。
- 涉及命令时，给出可直接复制的命令。
- 涉及代码改动时，说明影响范围、需要补充的测试、是否需要更新文档或变更记录。
- 信息不足时，指出需要读取的项目文件或需要确认的事实；不得用猜测替代项目事实。
