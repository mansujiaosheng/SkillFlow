SkillFlow 需求说明文档
1. 项目名称
SkillFlow
2. 项目定位
SkillFlow 是一个本地桌面端的 Agent Skill 可视化创建、规范化生成与流程编排工具。
它的核心目标不是运行 AI Agent，也不是做完整的工作流自动化平台，而是帮助用户通过 GUI 创建、管理、编排和生成标准化的 Skill 文件。
用户可以在图形界面中创建项目、拖拽 Skill 节点、配置节点信息、添加规则块、用连线描述 Skill 之间的关系，最后自动生成并落地标准化的 SKILL.md、项目配置文件、流程文件和检查报告。
3. 技术选型
本项目采用以下技术栈：
Tauri + React + React Flow + TypeScript + SQLite/JSON 文件
具体说明：
桌面框架：Tauri
前端框架：React
流程画布：React Flow
开发语言：TypeScript
本地存储：SQLite + JSON 文件
样式方案：可使用 Tailwind CSS / shadcn/ui
文件落地：通过 Tauri 后端写入本地文件系统
AI 接口：预留 OpenAI / Claude / 本地模型接口
4. 核心目标
本项目要实现以下能力：
1. 用户可以创建一个本地 Skill 项目。
2. 用户可以选择项目保存位置，程序自动创建项目文件夹。
3. 用户可以在空白大画布中拖拽 Skill 节点。
4. 用户可以点击 Skill 节点，编辑技能名、描述、使用时机、输入、输出、执行流程等内容。
5. 用户可以拖拽规则块到 Skill 节点中，例如 #require、#forbid、#check、#tool、#handoff。
6. 用户可以创建多个 Skill 节点，并用流程线连接它们。
7. 流程线可以描述 Skill 之间的关系，例如前置依赖、输出交接、审查关系、失败回退等。
8. 用户可以手写 Skill 内容，也可以让 AI 根据节点信息和节点关系自动生成 Skill。
9. 用户点击保存后，项目数据和生成结果必须自动落地到本地文件夹。
10. 系统应支持后续添加 Skill 质量检查器，也就是 Linter。
5. 非目标范围
第一阶段不要实现以下能力：
1. 不需要真正执行 Agent。
2. 不需要执行用户生成的 Skill。
3. 不需要运行 shell 命令。
4. 不需要做完整工作流自动化。
5. 不需要接入复杂的多 Agent 调度系统。
6. 不需要做云端同步。
7. 不需要做多人协作。
第一阶段只做：
项目创建
节点拖拽
节点编辑
规则块配置
流程线连接
保存落地
生成 SKILL.md
6. 用户使用流程
6.1 打开程序
用户打开 SkillFlow 后，进入一个空白首页。
首页提供以下操作：
新建项目
打开已有项目
最近项目列表
设置
6.2 新建项目
用户点击“新建项目”，弹出项目创建窗口。
用户需要填写：
项目名称
项目描述
项目保存位置
目标平台
目标平台可以包括：
Claude Code
OpenAI Codex
Trae
通用 Agent Skills
用户选择一个本地目录后，程序自动创建项目文件夹。
示例：
D:\AI-Skills\Android-CTF-Skills
自动生成目录结构：

8. 中间画布设计
中间画布使用 React Flow 实现。
用户可以：
1. 从左侧拖拽 Skill 节点到画布。
2. 移动节点位置。
3. 删除节点。
4. 复制节点。
5. 多选节点。
6. 用线连接节点。
7. 点击节点后在右侧编辑属性。
8. 点击线后编辑线的关系类型。
画布上的每个 Skill 节点代表一个独立的 Skill。
例如：
[00 全局规则] → [需求分析] → [代码修改] → [测试验证] → [文档更新] → [最终审查]
或者：
[安卓静态分析] → [Frida 动态调试] → [Flag 获取] → [WP 生成] → [质量审查]

10. 流程线设计
节点之间的线不能只是普通连线，必须带有语义。
第一版支持以下关系类型：
before        A 必须在 B 之前执行
depends_on    B 依赖 A 的输出
handoff       A 的输出交接给 B
review_by     A 的结果由 B 检查
fallback_to   A 失败后转到 B
parallel_with A 和 B 可以并行
每条线应支持配置：
关系类型
说明
传递数据
是否强制
备注
示例：
安卓静态分析 → Frida 动态调试
关系为：
handoff
传递数据：
关键类名
关键函数名
疑似校验逻辑
APK 包名
Hook 目标

16. AI 生成功能设计
AI 生成不能直接基于空白画布自由发挥。
正确流程是：
GUI 结构化数据
  ↓
转换为 JSON 上下文
  ↓
Prompt Builder 生成提示词
  ↓
AI 生成 SKILL.md
  ↓
Skill Linter 检查
  ↓
用户确认或修改
  ↓
保存落地
AI 生成按钮分为：
AI 补全当前节点
AI 重写当前 Skill
AI 优化 description 触发条件
AI 根据流程生成全部 Skill
AI 检查规则冲突
AI 生成 workflow.md

17. Linter 质量检查设计
Linter 是本项目的重要功能。它用于检查生成的 Skill 是否规范、完整、强约束、无明显冲突。
第一版检查规则：
1. 是否存在 YAML frontmatter。
2. 是否存在 name。
3. 是否存在 description。
4. description 是否包含明确触发条件。
5. 是否包含使用时机。
6. 是否包含输入。
7. 是否包含输出。
8. 是否包含必须遵守。
9. 是否包含禁止行为。
10. 是否包含执行流程。
11. 是否包含完成标准。
12. 是否出现弱约束词，例如：可以、建议、尽量、最好。
13. 是否出现危险行为，例如：自动删除文件、自动发送敏感信息、执行未知脚本。
14. 是否和全局规则冲突。
15. 是否存在孤立节点。
16. 是否存在循环依赖。
17. 是否存在没有下游交接说明的关键节点。
Linter 输出示例：
质量评分：86 / 100

严重问题：
- 缺少禁止行为
- 没有完成标准

警告：
- 出现弱约束词：“建议”
- 节点没有设置下游交接内容

建议：
- 增加 #check 规则
- 增加 #forbid 规则

21. 核心架构原则
本项目必须遵循以下原则：
GUI 是主控。
JSON 是事实源。
AI 是生成器。
Linter 是质量门。
SKILL.md 是最终产物。
也就是说：
用户控制结构，AI 补充内容。
用户控制规则，AI 优化表达。
用户控制流程，AI 生成落地文件。
不能让 AI 完全自由生成项目结构，也不能让 AI 覆盖用户明确写下的规则。
